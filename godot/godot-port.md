# Swapduel → Godot: port specification and implementation guide

Target: native iOS and Android builds of Swapduel in Godot 4.7, replacing the
Nuxt/Canvas client. The Node realtime server stays in place with one added
transport. The provisional web leaderboard remains web-only and is not part of
the native product.

This document is written against the current code:
`packages/game-engine` (1 400-line deterministic simulation), `apps/web`
(canvas renderer, input composables, Web Audio SFX, Socket.IO client),
`packages/contracts` (Zod schemas), `apps/server` (Express + Socket.IO).

---

## 1. What is actually being ported

| Layer | Today | Godot |
| --- | --- | --- |
| Simulation | `packages/game-engine/src/*.ts`, pure, immutable, 60 Hz fixed step, FNV-1a checksum | `game/engine/*.gd`, pure module functions over a mutable state object |
| Renderer | `app/game/renderer/drawBoard.ts` (1 382 lines of Canvas2D, offscreen panel sprite cache) | `Board2D` node with pooled `Sprite2D`s + `_draw` for effects |
| Input | `useBoardPointer.ts` (tap-select + horizontal swipe), `useBoardCursor.ts` (keyboard 2-wide cursor) | `_input` on the board node, same thresholds; cursor kept for desktop/editor testing |
| Audio | `useGameAudio.ts` — Web Audio oscillators/noise, synthesised at runtime | Baked `AudioStreamWAV` bank generated by the same synthesis math, pooled players |
| Netcode | `useRoomSocket.ts` (1 000 lines: Socket.IO, reconnect, attack retry/ack, clock sync, session storage) | `RoomClient` autoload over `WebSocketPeer` |
| Contracts | Zod schemas shared both ways | Server keeps Zod; client gets hand-written typed parsers generated from the same shapes |
| Competitive progression | Provisional private leaderboard | Deferred pending a better native product design |
| Persistence | `localStorage` / `sessionStorage` | `user://` config + recovery files |

The engine is the asset worth preserving exactly. Everything above it is a
rewrite, not a translation.

## 2. Language decision: GDScript

**Recommendation: GDScript, statically typed, for everything.**

Rationale:
- The .NET/C# mobile toolchain in Godot is the friction-heaviest path (per-platform
  .NET workloads, larger binaries, slower iteration, and historically the first
  thing to break on Godot upgrades). For a two-target mobile game with no other
  C# dependency, it buys only syntax familiarity.
- The workload is trivial for GDScript: 78 cells, ~30 live panels, one 60 Hz step
  that is mostly array indexing. Profiled equivalents run in tens of microseconds
  per step once the immutability is removed (see §3.2).
- Determinism is easier to control in GDScript because you are forced to be
  explicit; C# would tempt reuse of `Dictionary` iteration order and LINQ.

If you disagree and want C#: the port is mechanical (the TS is already
class-free and typed), but budget a week for the Android/iOS export toolchain
and accept that hot-reload iteration gets noticeably worse.

Use `class_name`-less static-function modules (`const Matches = preload(...)`)
to mirror the current module boundaries exactly.

## 3. Engine port

### 3.1 Module mapping

Port one-to-one; do not merge files. The existing split is good and the test
suite is organised along the same lines.

```
packages/game-engine/src/        →  game/engine/
  types.ts                       →  types.gd            (state classes + enums)
  config.ts                      →  config.gd           (GameConfig resource)
  random.ts                      →  rng.gd
  board.ts                       →  board.gd
  matches.ts                     →  matches.gd
  gravity.ts                     →  gravity.gd
  scoring.ts                     →  scoring.gd
  attacks.ts                     →  attacks.gd
  cancellation.ts                →  cancellation.gd
  garbage.ts                     →  garbage.gd
  danger.ts                      →  danger.gd
  recovery.ts                    →  recovery.gd         (snapshot ser/de)
  simulation.ts                  →  simulation.gd       (fixedStep + public API)
```

`simulation.gd` must keep the exact step order from `fixedStep`
(`simulation.ts:1052`), because several behaviours depend on it:

```
1. time-limit check (with the 1e-6 slack — see §3.3)
2. complete pending swap
3. advance_resolution   (stray-swap release → clear groups → garbage conversion
                         → per-panel gravity → find matches → begin resolution)
4. sync_phase_summary
5. advance_chain_closure
6. advance_garbage_lifecycle
7. sync_phase_summary        ← yes, twice
8. advance_danger_state
9. advance_rise
```

### 3.2 Mutability: the single biggest design change

The TS engine is purely immutable — every step spreads the whole state,
`cloneCells` copies 78 objects, `withPanelsById` rebuilds the grid. That is
idiomatic TS and disastrous in GDScript (per-frame allocation, GC churn on
mobile).

Port to **in-place mutation with explicit cloning**:

- `SimulationState`, `Board`, `Panel`, `GarbageBlock`, `ClearGroup`,
  `ChainState` become `RefCounted` classes with typed fields and a
  `duplicate_deep()` method.
- Panels live in a flat `Array[Panel]` of size `columns * visible_rows`, indexed
  `row * columns + column`, plus a separate `incoming_row: Array[int]`. Keep the
  `row = 0 is bottom` convention — the renderer, input math and snapshots all
  assume it.
- Every function that returned a new state now mutates `state` and returns
  `void`. `request_swap` returns a small `SwapResult` since it has a reason enum.
- `duplicate_deep()` is called in exactly three places: recovery snapshots, the
  cross-engine test harness, and never per-frame.
- Panels get pooled: a free-list on `Board` so `next_panel_id` allocation does
  not create objects mid-round.

Everything else about the algorithms stays literal. Resist "improving" the chain
closure or gravity logic during the port — the comments in `simulation.ts`
document hard-won behaviour (unrelated-clear-during-live-chain, the
`pendingSwap` row-shift on manual raise at `simulation.ts:1009`, the
stray-`swapping` backstop at `releaseStraySwapStates`).

### 3.3 Determinism

The engine is the source of truth for match fairness (both clients run it
independently and report checksums), so this section is not optional.

1. **Time is integer steps, not float milliseconds.** Today `elapsedMs` is a
   float accumulating `1000/60`, which is why `fixedStep` needs a `1e-6` slack
   against the time limit (`simulation.ts:1070`) and why the checksum has to
   `toFixed(4)` everything. In Godot, store `step: int` and derive
   `elapsed_ms := step * 1000.0 / 60.0` only for display. All timers
   (`animation_started_at`, `phase_started_at`, `next_cell_at`, `ready_at`,
   `closing_started_at`) become step counts; every duration constant in
   `config.gd` is converted to steps at load with `roundi(ms / (1000.0/60.0))`.
   This removes the entire class of float-drift desync and lets the checksum
   hash integers.
2. **`riseOffset` stays a float** (it is sub-cell position) but must be
   `float` = f64 in GDScript, matching JS `number`. Godot's `float` is f64, so
   parity with the TS engine holds. Do **not** store it in a `Vector2` or any
   packed array (those are f32).
3. **RNG**: port `random.ts` bit-for-bit. `seedToRandomState` and `nextRandom`
   use `Math.imul` and `>>> 0`; GDScript ints are 64-bit signed, so wrap every
   multiply: `(a * b) & 0xFFFFFFFF`. Write a `rng_test.gd` that asserts the
   first 1 000 outputs match a fixture captured from the TS implementation.
4. **Never** use `randi()`, `Time.get_ticks_*`, dictionary iteration order, or
   `Array.sort()` without a comparator inside the engine.
5. **Checksum**: port `simulationChecksum` exactly, including field order and
   separators. It must produce the same 8-hex-digit FNV-1a value as the TS
   version for an equivalent state — this is what makes §7.2 possible.

### 3.4 Config

`config.gd` mirrors `defaultGameConfig` as a `Resource` so it is tweakable in
the editor, but the shipping values are loaded from a checked-in `.tres`
generated from `config.ts`. Attack/scoring/combo tables become
`Array[Dictionary]` with the same `{minimum, maximum, ...}` shape so
`comboAttackBlocks`/`clearScore` port unchanged.

Keep `timeTrialDurationMs = 120_000` and the tuned rise curve
(`startingRowsPerSecond: 0.12`, 15 s interval, ×1.12, cap 0.5, manual 0.9,
`manualStopDrainMultiplier: 3`) exactly — those numbers are the result of the
tuning commits in git history.

## 4. Presentation

### 4.1 Scene tree

```
Main (Node)                        autoloads: Game, RoomClient, Audio, Settings
├── ScreenStack (CanvasLayer)
│   ├── HomeScreen
│   ├── EndlessScreen ─┐
│   ├── TimeTrialScreen├─ all embed BoardView
│   ├── RoomScreen     │
│   └── MatchScreen ───┘  (embeds two: own BoardView + OpponentBoardView)
└── SafeArea (MarginContainer)     driven by DisplayServer.get_display_safe_area()
```

`BoardView` is the reusable unit: aspect-locked 1:2 `SubViewportContainer`
(or a plain `Control` with a fixed design resolution of 360×720 and
`canvas_items` stretch), a `Node2D` board, and an overlay `Control` for badges.

### 4.2 Rendering strategy

`drawBoard.ts` already discovered the right shape: panels are pre-rasterised per
(type, variant, cellSize, dpr) into an offscreen canvas and blitted. Godot gives
you that for free — but do it as *authored assets*, not runtime rasterisation:

- **Panels**: one `AtlasTexture` per (type × variant) where variant is
  `idle | flashing | incoming`, 7 types × 3 = 21 regions in a single atlas.
  Author them at 128 px and let Godot scale; the current procedural
  gradient/bevel/symbol drawing becomes the design spec for the artist (or a
  one-off export script that runs the existing canvas code and saves PNGs).
- **Panel nodes**: a pool of `Sprite2D`s sized `columns * visible_rows + slack`
  (~90), parented to the board `Node2D`, positioned each frame from engine
  state. No node creation during a round. Swap/fall/squash offsets go on
  `position` and `scale`; the flash pop is a variant swap plus `modulate`.
  Alternative if you want a single draw call: `MultiMeshInstance2D` with
  per-instance custom data selecting the atlas region. Start with sprites;
  78 sprites is nothing, and it keeps per-panel tweening trivial.
- **Garbage slabs**: `NinePatchRect`-style tiling drawn per cell
  (`drawGarbageTile` semantics: bevel, metal diagonal streak, rivet/lozenge
  centre mark, `heat` whiteout during conversion). Two skins, `normal` and
  `metal`, matching `GARBAGE_SKINS`.
- **Effects** (combo/chain badges, particles, telegraph queue chips, stop-time
  bar, danger tint, panic vignette): keep in `_draw` on an overlay `Node2D`, or
  as short `AnimationPlayer`/`Tween` sequences. Port `impact.ts` verbatim — it
  owns the landing shake, squash and `panicIntensity` curve, and it is only
  225 lines.
- **The rise offset** shifts the whole board container by
  `-rise_offset * cell_size` and the incoming row is drawn desaturated below
  (the `incoming` sprite variant).

### 4.3 Frame pacing

The web client runs a hand-rolled accumulator (`animationLoop` in `solo.vue`),
throttles rendering to ~30 fps and reactive UI to 10 Hz, because of battery.
In Godot:

- Simulation runs in `_physics_process` with
  `Engine.physics_ticks_per_second = 60`. Do **not** use the accumulator
  pattern; Godot's physics tick *is* the fixed step. Set
  `Engine.max_physics_steps_per_frame = 8` so a hitch cannot burst-simulate.
- Rendering runs in `_process`. Ship at 60 fps
  (`Engine.max_fps = 60`); the 30 fps cap in the web client was a Canvas2D/DOM
  cost, not a GPU one. Expose a "battery saver" setting that drops to 30.
- Interpolate visuals between physics ticks using
  `Engine.get_physics_interpolation_fraction()` for panel fall/swap offsets only.
  Everything else can snap.
- HUD labels update on signal, not per frame — the engine emits
  `score_changed`, `chain_started`, `clear_resolved`, `danger_entered`.

### 4.4 Input

Port `useBoardPointer` semantics exactly; they are tuned and tested:

- Tap a panel, then tap an adjacent panel in the same row → swap.
- Horizontal drag past `SWIPE_THRESHOLD = 0.28` of a cell → swap that direction.
- Vertical travel > 8 px before triggering → gesture rejected (no vertical
  swaps exist in this game; the drag must feel *ignored*, not broken).
- Coordinate math is
  `column = floor(local_x / cell)`,
  `row = floor((height - local_y) / cell - rise_offset)`.

In Godot use `_gui_input`/`_input` with `InputEventScreenTouch` and
`InputEventScreenDrag` (`emulate_mouse_from_touch` on for editor testing).
The raise button keeps the 80 ms hold delay before `set_manual_raise(true)`
(`solo.vue:254`) so a tap on it does not nudge the stack.

Add on mobile, which the web client could not do well:
- Haptics on clear/chain/garbage-landing via `Input.vibrate_handheld()`
  (short, gated behind a setting).
- Keep `useBoardCursor` as a desktop/debug input map — it is how you will
  playtest in the editor.

### 4.5 Audio

`useGameAudio.ts` synthesises everything at runtime (oscillator sweeps + filtered
noise, ascending arpeggio per clear size, panic layer, danger beep). Godot has no
equivalent to Web Audio's scheduling graph, and `AudioStreamGenerator` on mobile
is a bad place to live.

Plan:
1. Write a one-off script (Node, reusing the existing math) that renders each
   effect to a 44.1 kHz mono WAV: `swap`, `clear_1..clear_n` arpeggio steps,
   `chain_2..chain_13`, `garbage_land_small/med/large`, `panic_1..3`, `danger`,
   `win`, `lose`, `countdown`.
2. Import as `AudioStreamWAV`, group under an `Audio` autoload with a pool of
   ~12 `AudioStreamPlayer`s and the same rate-limiting `recentlyPlayed(key, gapMs)`
   guard.
3. Buses: `Master → SFX`, with the existing 0.24 master gain as the bus default.
4. iOS/Android: no unlock gesture is needed (that was a browser rule) — delete
   `unlockAudio`. Do respect `AudioServer` interruption on incoming calls.

The sound preference persists to `user://settings.cfg` instead of localStorage.

## 5. Networking

### 5.1 The Socket.IO problem

Godot has no maintained Socket.IO client, and writing one against Engine.IO's
framing is a liability. Do not do it.

**Add a plain WebSocket endpoint to the existing server** that speaks the same
message names and the same Zod-validated payloads, and have Socket.IO and the
new endpoint feed the same room/match logic.

`apps/server/src/index.ts` already routes everything through a thin
`socket.on(name, payload)` → domain-call → `io.to(...).emit(name, payload)`
shape, so extract that into a transport-agnostic layer:

```
apps/server/src/
  transport/socketio.ts     existing behaviour, unchanged for the web client
  transport/websocket.ts    new: `ws` server on /ws, JSON frames
  transport/session.ts      shared: socket id ↔ player, rooms, broadcast helpers
  handlers/*.ts             the existing room/match/attack logic, moved as-is
```

Frame format (one JSON object per message, both directions):

```json
{ "e": "attack:send", "d": { ...exact existing payload... } }
```

Room membership/broadcast is a `Map<roomId, Set<Connection>>` in
`transport/session.ts`. Everything else — rate limits, `KNOWN_CLIENT_EVENTS`,
Zod validation, attack sequencing and retry, the 150 ms simultaneous-top-out
window, checksum tracking, room cleanup timers — is reused untouched.

This is a genuinely small change (a day or two) and it means the Godot client
can be a ~400-line `RoomClient` instead of a protocol reimplementation.

### 5.2 `RoomClient` autoload

Port the responsibilities of `useRoomSocket.ts`, which are: connect/reconnect
with credentials, room state mirror, round preparation/starting handshake,
opponent snapshot relay at ~10 Hz, attack send with local retry until
`attack:confirmed`, attack ack on receive, checksum reporting every 2 s,
clock sync via `ping`/`pong` with `selectBestClockEstimate`, and pause/resume
on connection loss.

Godot specifics:
- `WebSocketPeer` polled in `_process` on the autoload; parse in a loop until
  the queue drains.
- Signals out: `room_state_changed`, `round_prepared`, `round_starting`,
  `opponent_snapshot`, `attack_incoming`, `attack_confirmed`, `round_ended`,
  `match_ended`, `match_paused`, `match_resuming`, `desync_detected`.
- Reconnect: exponential backoff, credentials (`roomId`, `playerId`,
  `reconnectToken`) stored in `user://session.cfg`. The server already holds
  a slot for 5 minutes and replays unacked attacks to the replacement socket.
- Clock: keep `estimateServerClock` / `selectBestClockEstimate` from
  `contracts` — port those two functions to `clock.gd`, they are 20 lines and
  round start times depend on them.
- **Backgrounding**: replace the `visibilitychange` handling with
  `NOTIFICATION_APPLICATION_PAUSED` / `_RESUMED`. On resume: stop the
  simulation, re-sample the clock, take the lowest-RTT estimate, reset frame
  timing, then resume — same recalibration the web client does, and it matters
  more on mobile where the OS suspends aggressively.

### 5.3 Contracts

Server keeps Zod as the single authority. For the client, hand-write
`game/net/messages.gd` with one `parse_x(dict) -> X or null` per message. Two
rules:
- Reject unknown/missing fields loudly in debug, drop silently in release
  (matching the current `strict()` posture).
- `PROTOCOL_VERSION` is checked on every inbound message; a mismatch surfaces
  an "update the app" screen rather than desyncing.

Because the app store update cycle now decouples client and server versions,
bump `PROTOCOL_VERSION` to 2 for the Godot protocol and have the server accept
both 1 (web) and 2 (native) during the transition.

### 5.4 Competitive progression

Do not port the provisional `GET/POST /api/leaderboard` flow into the native
client. It was built for a small private web audience and is not the intended
long-term product feature. Keep native time-trial results local until a better
progression or competition model has been designed deliberately.

## 7. Testing

### 7.1 Port the suite

`packages/game-engine/tests` has 16 files covering matches, gravity, chains,
cancellation, garbage, attacks, danger, scoring, recovery, swap-during-raise,
concurrent resolution, time-trial, simulation, soak and random boards. Port all
of them to gdUnit4. The helpers file (`tests/helpers.ts`) — board literals,
step-until predicates — ports first and everything else follows cheaply.

Do not skip `soak.test.ts` and `random-board.test.ts`; they are what catch the
"panel stuck in `swapping` forever" class of bug.

### 7.2 Cross-engine conformance harness

This is the highest-value piece of the whole port and should exist before the
first screen is built.

1. Define a trace format: `{ seed, config_hash, timeLimitMs, inputs: [{step, kind, row, column, direction}], attacks: [{step, ...}] }`.
2. `tools/conformance/run-ts.mjs` runs the TS engine over a trace and emits the
   checksum at every 30th step to a `.jsonl` fixture.
3. `tests/conformance_test.gd` runs the GDScript engine over the same trace and
   asserts every checksum matches.
4. Generate 500 random traces once, commit the fixtures, run in CI.

If the checksums match across 500 traces, the port is correct — and as a bonus
the two clients can play each other, which makes rollout a non-event.

Note this requires §3.3 step-integer timing on *both* sides: convert the TS
engine to integer steps first, verify its own tests still pass, then port. That
ordering saves you from chasing float divergence.

### 7.3 Device testing

Real-device matrix before ship: one low-end Android (4 GB, 60 Hz), one recent
Android, iPhone SE-class, and a notched iPhone (safe area). Watch for: thermal
throttling during a 2-minute time trial, audio latency on the swap sound
(should be < 40 ms perceived), and touch registration at the board edges.

## 8. Phasing

Each phase ends with something runnable.

**Phase 0 — prep (server + TS side), ~3 days**
- Convert the TS engine to integer-step timing; all existing tests green.
- Build the conformance trace generator and fixtures.
- Bake panel atlas and audio WAVs from the existing canvas/Web Audio code.

**Phase 1 — engine port, ~1.5 weeks**
- `game/engine/*` complete, mutable-state design, panel pooling.
- gdUnit4 suite ported; conformance harness green over 500 traces.
- No visuals. This phase is done when checksums match, not when it looks right.

**Phase 2 — playable endless, ~1.5 weeks**
- `BoardView` with panel pool, garbage slabs, rise, danger tint.
- Touch input (tap-select + swipe), raise button, `impact.gd` shake/squash.
- Audio bank wired. HUD (score/time/best). `user://` settings and best score.
- Ships as a testable APK/IPA of the endless mode.

**Phase 3 — time trial, ~2 days**
- 2-minute timed run, final-stretch clock, result screen.
- Local best score and interruption recovery; no remote ranking.

**Phase 4 — transport split on the server, ~2 days**
- Extract `transport/`, add the WebSocket endpoint, protocol version 2.
- Existing web client must be unaffected — its Socket.IO tests stay green.

**Phase 5 — online duel, ~2.5 weeks**
- `RoomClient`: create/join/reconnect, ready state, round handshake,
  countdown on synced clock.
- Opponent board view fed by the ~10 Hz snapshot relay.
- Attack send/retry/ack, incoming telegraph queue, checksum reporting.
- Pause/resume on disconnect, 30 s recovery window, round/match resolution,
  rematch.
- Application-pause recalibration and crash recovery snapshot to `user://`.

**Phase 6 — store readiness, ~1 week**
- Icons, splash, export presets, signing, privacy manifest (iOS), target SDK
  (Android), age rating, store listings.
- Battery-saver mode, haptics setting, accessibility (reduced motion already
  exists as a flag in the renderer — honour `DisplayServer` where available,
  otherwise expose it as a setting).

Roughly 7–8 weeks of focused work for one developer, with Phase 5 carrying most
of the risk.

## 9. Risks and open decisions

| Risk | Mitigation |
| --- | --- |
| Float divergence between the two engines desyncs cross-play | §3.3 integer steps + §7.2 conformance harness, done first |
| Immutable→mutable port introduces aliasing bugs (a panel referenced in two cells) | Panel pool with an `owner_index` assertion in debug builds; the soak test catches most of it |
| Socket.IO → WebSocket transport split regresses the live web client | Transport-agnostic handler extraction with the existing server tests as the gate |
| Client/server version skew once shipping through app stores | Dual protocol version support, server-side minimum-version gate with a friendly update screen |
| A provisional ranking becomes accidental product scope | Keep it web-only; design native competitive progression separately |
| GDScript perf on low-end Android | Board work is trivial post-mutability; the real budget goes to draw calls — keep panels in one atlas, profile with the Godot mobile profiler on the low-end device from Phase 2 onward |

Open questions worth deciding before Phase 5:
1. Does the web client stay live after the native launch? If yes, cross-play is
   effectively mandatory and §7.2 becomes a permanent CI gate. If no, Phase 4
   can be a straight replacement rather than an addition.
2. Do you want matchmaking, or does private-room-code-only remain the model?
   The current server assumes the latter throughout.
3. Push notifications for "your friend is waiting" — not in the current design,
   but it is the one native affordance that would change the room flow.
